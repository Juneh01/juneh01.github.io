ASA Agent - Agentic Training Content Platform

项目概览

ASA Agent 是我在 Apple 北京实习期间参与设计与实现的智能培训内容平台。项目希望把原本分散的产品知识整理、内容规划、内容生成、质量检查、人工审核和交付流程，连接成一条可追踪、可复核、可持续迭代的 Agentic Workflow。

平台并不把大语言模型当作一个直接输出答案的黑盒，而是将复杂任务拆分为知识接入、证据对齐、内容规划、多 Agent 生成、自动验证、人工审核和版本化交付等阶段。每个阶段都有结构化输入输出、状态记录和明确的失败处理方式，使生成内容能够回溯到依据，也能在局部出现问题时进行定向修复。

English summary: I contributed to an agentic training-content platform that connects multi-source knowledge ingestion, evidence-grounded planning, specialized content-generation agents, automated quality gates, human review, and versioned delivery. This public summary intentionally abstracts internal data, product details, prompts, services, evaluation sets, and deployment endpoints.

背景与问题

面向培训场景生成内容，比普通文本生成更强调事实一致性、覆盖完整性和交付稳定性。实际工程中主要存在以下挑战：

  • 知识来源异构：结构化规格、层级标签、说明文档和营销材料的粒度与表达方式不同。
  • 内容形态多样：题目、短视频脚本、直播脚本和销售对话拥有不同的结构、语气和质量标准。
  • 生成过程不可完全确定：模型输出需要经过解析、验证、重试与人工复核，不能直接进入交付环节。
  • 证据需要可追溯：生成内容必须保留来源标识与检索上下文，便于审核事实依据。
  • 工作流需要可运营：长任务必须异步执行，并支持进度查看、单项编辑、拒绝、重生成和导出。

因此，项目的核心不是“写一个 Prompt”，而是构建一套围绕 LLM 的可靠内容生产系统。

我的工作

我围绕平台的端到端工程化参与了以下工作：

  1. 设计多源知识进入统一语义层的适配与对齐流程，使不同来源可以被标准化、验证并保留来源信息。
  2. 建立任务无关的内容种子契约，将层级信息、内容范围、证据包和规划来源统一封装，避免各生成模块重复处理数据。
  3. 实现面向多种内容形态的 Agent 生成链路，包括输入适配、结构化生成、解析、校验、带反馈重试与结果序列化。
  4. 构建 FastAPI 后端与 React/TypeScript 审核工作台，支持任务状态、内容预览、人工编辑、审核、单项重生成和多格式导出。
  5. 使用 MySQL 保存产品、任务、内容与审核状态，使用 Redis 处理异步任务路由，将持久记录与短生命周期执行状态分离。
  6. 完善契约测试、接口测试、检索测试、Agent 测试和端到端 Smoke Test，并通过审计模式在调用模型前验证输入与证据边界。

系统架构

平台可以抽象为以下流程：

工程实现分为四个主要层次：

层次 主要职责
Knowledge Layer 接入不同格式的知识，统一层级、字段和来源标识，形成可检索的证据单元。
Agent Layer 根据共享内容种子运行不同生成任务，并负责解析、验证、重试和结果构造。
Runtime Layer 通过 API、异步队列和持久化存储管理任务、状态、内容版本与审核记录。
Review Layer 提供可视化工作台，支持查看证据、比较结果、编辑、审核、重生成和导出。

多源知识接入与对齐

不同知识源往往不能直接合并：同一个概念可能使用不同名称，有的来源强调层级关系，有的来源强调事实描述，还有的来源更接近面向用户的表达。平台通过 Adapter 将来源转换为统一中间结构，再进行字段校验、粒度检查、归一化和对齐。

这一阶段重点解决三个问题：

  • 稳定标识： 为知识单元建立稳定 ID，使后续规划、生成、审核和版本更新引用同一对象。
  • 事实与表达分离： 将可验证事实和面向内容生成的表达材料分别保存，降低营销语言覆盖技术事实的风险。
  • 来源追踪： 在证据包中保留来源 ID、检索方式和命中信息，让审核者可以理解生成依据。

对于无法可靠匹配、粒度过粗或存在歧义的输入，流程会优先记录问题并进入审核，而不是强行生成下游内容。

Content Seed：共享生成契约

平台使用任务无关的 Content Seed 作为知识层与生成层之间的边界。一个 Seed 表示一个已选择的内容范围，并携带：

  • 产品或主题标识；
  • 层级位置、内容描述与细粒度知识项；
  • 规划来源与覆盖信息；
  • 结构化事实和检索证据；
  • 来源 ID 与审计元数据。

题目、短脚本、直播脚本和销售对话等模块不会各自重新读取原始数据，而是由轻量 Adapter 将同一个 Seed 转换为模块需要的输入。这种设计减少了重复逻辑，也让不同内容类型共享一致的事实边界。

检索与证据链

RAG 层同时考虑精确事实检索和语义表达检索。系统会先根据内容范围映射相关知识组，避免把整份知识库无差别塞入上下文；随后结合关键词检索与向量检索，在需要时融合排序结果。

检索结果不只返回文本，还会记录命中来源、证据 ID、排序方式、字符预算和缺失原因。这样可以回答两个关键问题：

  1. 生成内容使用了哪些依据？
  2. 如果结果有问题，应该刷新证据、调整规划，还是只重生成当前内容？

多 Agent 内容生成

平台为不同内容类型设置专用 Agent，而不是用一个通用模板覆盖所有任务。

Quiz Agent

题目生成链路包含可出题性判断、题干与选项生成、答案解析、规则校验和最终审核。对于缺乏实际考点的知识项，前置质量门会提前终止，避免无意义生成。

Script Agents

短视频、直播和销售场景分别使用不同的结构化输入与输出契约。生成过程会考虑时长、受众、内容范围和参考证据，并对段落结构、长度、事实引用和输出格式进行验证。

QA and Repair

校验失败不会简单地从头重跑全部流程。系统根据错误类型选择局部路径：格式或长度问题进入带反馈重试，证据不足触发检索刷新，覆盖缺口回到规划，人工拒绝则保留意见并重生成单项内容。

Human-in-the-Loop 工作台

LLM 负责扩展内容生产能力，人工审核负责最终质量边界。审核工作台围绕真实工作流提供以下能力：

  • 查看任务进度和每个内容项的生成状态；
  • 阅读生成结果、结构化字段、证据与执行记录；
  • 直接编辑内容并保存人工版本；
  • 批准、拒绝并记录审核意见；
  • 仅重生成不合格的单项内容；
  • 导出经过筛选的 JSON、Markdown 或表格交付物。

前端负责交互和状态呈现，FastAPI 提供统一接口；MySQL 是持久化事实来源，Redis 只承担队列和短期运行路由，避免任务重启后丢失审核与编辑记录。

可靠性与工程质量

项目中的可靠性设计主要体现在以下方面：

  • 使用 Pydantic 契约约束 Agent 之间的数据形状，减少隐式字典传递。
  • 对输入缺失、层级歧义和无效映射采取 fail-fast 策略。
  • 在正式调用 LLM 前提供 audit-only 模式，验证 Seed、证据和任务适配结果。
  • 将生成、解析、验证与输出序列化拆分，便于单元测试和局部替换。
  • 对模型调用保留脱敏 Trace 和错误上下文，支持定位非确定性失败。
  • 通过自动测试覆盖知识适配、检索、Agent、API、持久化和工作流关键路径。
  • 将凭据保留在运行环境中，公开文档与代码路径不记录真实 Token、内部地址或原始业务数据。

项目收获

这个项目让我更系统地理解了 Agent 应用从原型走向可用平台时真正困难的部分：模型能力只是其中一环，稳定的数据契约、证据管理、异步运行、失败恢复、人工审核和版本追踪同样重要。

相比一次性生成，可靠的 Agent 系统更接近一个由状态、契约和质量门组成的软件系统。它需要知道何时生成、依据什么生成、失败后回到哪一步，以及最终由谁确认。这些经验也进一步连接了我对 Agent Memory、AI Infrastructure 和部署导向系统设计的研究兴趣。
